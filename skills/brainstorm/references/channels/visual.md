# Channel: Visual

Two distinct jobs. Decide which (if either) applies in the moment.

## 1. Diagram-to-THINK (the primary use here)

The user has said seeing something mapped in space — a flowchart or diagram — genuinely helps them
conceptualize. Reach for a diagram whenever a **structure, flow, or set of relationships** is clearer
seen-in-space than described in prose. Match the diagram type to the cognitive move:

- **flowchart / sequence** → a process or pipeline
- **decision tree / branch** → forks, options, "if this then that"
- **node-graph / map** → relationships, dependencies, how parts connect
- **2×2 or landscape** → an option space along two axes

Render inline where possible (e.g. Mermaid). Treat the diagram as a **shared artifact both parties point at**
and co-evolve as the conversation moves — update it as decisions lock.

**Fidelity is a divergence dial.** While diverging, keep diagrams **rough, partial, low-fidelity** — the
incompleteness is a feature: partial visuals increase divergence and reduce fixation, and the "stroke talks
back." A polished, complete diagram mid-exploration anchors the user and converges them early. Crisp up only
when convergence is real.

## 2. Mockup-to-PREVIEW (build/feature work)

For UI/feature work, a real mockup the user can react to beats prose — the single cleanest design successes
came from a mockup in the loop. Same fidelity rule: rough while exploring the layout, clean only to commit.

## When NOT to

Conceptual or evaluative questions (definitions, tradeoff judgments, "what does X mean here") are text — don't
diagram them. A visual topic is not the same as a visual *question*.
